Append-only log of decisions, gotchas discovered, and lessons for the web app.

## What Works

- **`formatCost` 3 sig figs for sub-cent** — use `Math.floor(Math.log10(usd))` to get the leading digit's magnitude, then `dp = -magnitude + 2` for exactly 3 significant figures. Don't strip trailing zeros for sub-cent amounts — they're significant. Only strip for `$0.01–$0.99` range.

- **Hover popovers must portal to `document.body` + `position: fixed`** — the new generic `HoverCard` (`vendor/ui/kit/HoverCard.tsx`) measures the trigger via `getBoundingClientRect()` and renders the card through `createPortal`. Absolute positioning inside the PR-list table / timeline rows gets clipped by row `overflow`, so don't reach for the click-based `Dropdown` (which uses `position:absolute`) for hover previews. Close on a ~120ms delay (on both trigger and card `mouseleave`, cleared on re-enter) so the pointer can travel into the card to click the `file:line` links; close on scroll/resize to avoid a stale fixed position.

- **Line-numbered "code editor" = disable soft-wrap, sync the gutter's `scrollTop`** — `vendor/ui/kit/CodeTextarea.tsx` puts a fixed-width number gutter next to a real `<textarea>`. The trap is soft-wrap: a wrapped logical line occupies 2+ visual rows and the 1:1 gutter numbering desyncs. Fix is `wrap="off"` + `whiteSpace:"pre"` on the textarea (one logical line = one visual row; long lines scroll horizontally), and mirror the textarea's vertical scroll onto the gutter via `onScroll → gutterRef.scrollTop = ta.scrollTop`. Gutter + textarea must share identical `fontSize`/`lineHeight`/top-padding or the numbers drift. It stays a controlled `<textarea value/onChange>`, so `getByDisplayValue` RTL tests keep working — the ConfigTab test needed no change when swapping `Textarea`→`CodeTextarea`.

- **2026-10-25 — Visual check without the Chrome extension: use the global `agent-browser` CLI (the one e2e uses) with its own session.** `agent-browser --session diag set viewport 1440 900`, then `open <url>`, `wait --text "…"`, `screenshot "figure" out.png`, and `eval '<js>'` to measure things like `scrollWidth` vs `clientWidth`. Close it with `agent-browser --session diag close`. A named session keeps it off the `default` one that e2e runs use. Element screenshots of a wide scroll container can look cropped, so trust the `eval` measurements or a viewport screenshot instead.

- **2026-10-25 — A `display: grid` with no `gridTemplateColumns` lets a wide child overflow the page, even when that child is `overflow-x: auto`.** The implicit `auto` track sizes to the child's min-content, and an overflow-auto box still reports its content width as its min-content contribution. The onboarding page's `s.content` grew to 1236px inside an 878px column. Fix: `gridTemplateColumns: "minmax(0, 1fr)"` on the grid (as in `OnboardingView/styles.ts`). `minWidth: 0` on the grid itself is not enough.

- **2026-10-25 — SVG-under-HTML diagrams: put edge labels in a second SVG layer ABOVE the nodes.** `ArchitectureDiagram` draws arrows in an SVG behind absolutely-positioned HTML nodes. Labels in that same SVG were hidden by the nodes. Edges that skip a column also passed under the middle node and looked like they came from it. The fix: a labels-only overlay SVG (`pointer-events: none`, `auto` on each `<g>` so `<title>` tooltips work), with a background pill per label. Skip-column edges route along the empty `GAP_Y` strips between rows. Pure geometry lives in `ArchitectureDiagram/helpers.ts`, with tests.

- **There is no Prettier config in `client/`. `npx prettier --write` falls back to `printWidth: 80` and reflows a file written in the repo's ~120-column style.** Don't run it on a whole file. If you already did, `--print-width 120` restores most of it, and you may still need to fix a few spots by hand.

## What Doesn't Work

- **`PrDetail.files` (from `GET /pulls/:id`) is NOT guaranteed unique per `path` — keying diff cards by `f.path` crashes React on some PRs.** `pr_files` has no unique `(pr_id, path)` constraint, and at least one imported PR (PR #2, "Conventions Extractor…") carries TWO rows for the same file (`CLAUDE.md` as `+1/-0` AND `+0/-61`; same for `client/CLAUDE.md`) — separate diff fragments the importer stored as distinct rows. Both the shared `diff-viewer/DiffViewer` and the new `SmartDiffViewer`/`FileCard` used `key={f.path}`, so those PRs threw `Encountered two children with the same key` at render (React may then drop/duplicate cards). Not caught by any test because fixtures use unique paths, and not seen on most PRs. Fix (composition layer, NOT a `key={path+index}` hack — a file's diff belongs in one card): `dedupeFilesByPath` in `diff-viewer/helpers.ts` merges rows per path (sums +/- stats, concatenates the `@@` hunk fragments), called once in `DiffTab` before either viewer; the server `modules/smart-diff/service.ts` merges by path too so grouped-view data is unique. Before using any server-provided list as React keys, dedupe it — the DB/contract doesn't promise uniqueness.

- **Adding `useTranslations("<new-namespace>")` inside a widely-shared component silently breaks every existing caller that doesn't register that namespace in its `NextIntlClientProvider`.** `diff-viewer/FileCard.tsx` is consumed both by the plain `DiffViewer` (existing callers, `shell` namespace only) and the new `SmartDiffViewer` (needs `smart-diff` strings for the findings badge / mechanical placeholder). Calling `useTranslations("smart-diff")` unconditionally inside `FileCard` doesn't fail typecheck or most tests, but throws `IntlError: MISSING_MESSAGE` at render for any consumer whose provider doesn't include that namespace — caught only by `src/test/smoke.test.tsx`'s narrower `{shell: shellMessages}` provider logging the error to stderr (test still "passed" since next-intl swallows it and renders a fallback, so this is easy to miss). Fix: keep the shared component locale-agnostic beyond its original namespace — accept **pre-formatted strings** as props (`findingsLabel?: string`, `mechanicalPlaceholderText?: string`) with a plain-English fallback (`?? `${n} findings``), and do the actual `useTranslations("smart-diff")` call one level up, in the feature-specific caller (`SmartDiffViewer`) that already needs that namespace. Generalizes: before adding a new `useTranslations(ns)` call to a component with more than one caller, check every caller's `NextIntlClientProvider messages={...}` (tests especially) for that namespace, or push the translation call up to the caller instead.

- **A single flex-wrap row mixing a title with secondary metadata (edit icon, tag) gives inconsistent gaps depending on title length.** `ConventionCandidateCard`'s header originally put the rule title, an edit `IconBtn`, and a category tag all in one `flexWrap: "wrap"` container with a uniform `gap`. It looked fine for a short one-line title but looked cramped for a long title that wrapped to 2 lines — the metadata row that wrapped underneath only got the same small inline `gap` as spacing from the paragraph above, not a real margin. Fix: don't rely on wrap behavior for visually-distinct rows — split into an explicit column (`titleCol` → `titleRow` + `metaRow`, each its own flex row) with a real `gap` between them, so spacing is consistent no matter how many lines the title takes.

- **A capture-phase `window` scroll listener that closes a popover will block scrolling INSIDE it** — `HoverCard` closes on page scroll to avoid a stale `position: fixed`, but with `addEventListener("scroll", …, true)` the handler also fires for wheel-scrolls of the card's own inner list, instantly closing it. Guard with `if (cardRef.current?.contains(e.target)) return;` so only page scrolls close the card.

- **`ConventionCandidateCard`'s evidence `path:line` is rendered via `MonoLink` with NO `href`** — it degrades to a plain non-clickable button showing text only. `client/src/lib/github-urls.ts#githubBlobUrl` already exists and is used by `FindingCard`/`FindingsPopover` to build a clickable GitHub blob+line URL for PR-review findings, but nothing wires the same helper into the conventions candidate card. If the acceptance criterion is "clicking a candidate's evidence opens the real file on GitHub," this currently does NOT work — pass a `githubBlobUrl(...)` result as `MonoLink`'s `href` (needs repo owner/name + ref, not just path/line, which the candidate's evidence fields don't currently carry — check what `ConventionCandidate` needs added).

- **`ConventionCandidateCard`'s left border is intentionally always `var(--ok)` (green), NOT status-driven** — `styles.ts`'s `card()` used to color it by status (`accepted → var(--ok)`, `rejected → var(--text-muted)`, `pending → var(--border-strong)`), which looks like the "obviously correct" design (status at a glance) and matches how the Accept/Reject buttons still work (kind switches to `primary`/`secondary` per status). Explicit user design call: keep the border always green regardless of status — don't reinstate the status-color branching, that reverts a deliberate decision, not a bug fix. `card()`'s signature dropped its `accepted` param accordingly (now just `card(rejected: boolean)`, `rejected` still drives the dimmed opacity).

## Codebase Patterns

- **`FindingsPopover` is shared by the PR list and the detail timeline** — it lives at `app/repos/[repoId]/pulls/_components/FindingsPopover/` (the parent `pulls/` route, so both the list `page.tsx`/`PRRow` and the nested `[number]/_components/RunHistory` import it). It takes `findings: Finding[]`; `FindingRecord[]` (timeline reviews) is structurally compatible, so pass it directly. The timeline's per-run findings come for free from the already-loaded `usePrReviews` data — `FindingsTab` builds `findingsByRun` (`run_id → review.findings`) and threads it into `RunHistory`, which falls back to the old "N findings · M blockers" text when a run has no matching review (failed/running).

- **To make a whole row a hover trigger but anchor the card elsewhere, separate the hover area from the anchor** — `HoverCard` supports `block` (wrapper is a full-width `div`, so an entire timeline row is the hover area) + `anchorRef` (a ref to a child, e.g. the severity badges, used for `getBoundingClientRect` positioning). The timeline's `RunRow` (extracted so each row can own a `badgesRef`) wraps the whole row and points `anchorRef` at the badges. NOTE: you can't show a hover-highlight by tinting the `block` wrapper — the row's own `--bg-elevated` is opaque and sits on top; highlight the row element itself if needed. The non-`block` (inline `span`) mode keeps the plaque highlight for the PR-list badges.

- **`AppFrame`'s `<main>` (`vendor/ui/shell/AppFrame.tsx`) has zero padding by design** — every top-level page view is responsible for its own page-level padding, not the shell. The convention (see `AgentsListView`'s `s.page: { padding: "24px 32px 44px", maxWidth: 1100, margin: "0 auto" }`) is to wrap the page's root JSX in a `page` style from the view's own `styles.ts`. `ConventionsView` was scaffolded without this wrapper, so its content rendered flush against the viewport edge (no gutters) even though its layout otherwise matched sibling pages — easy to miss because nothing errors or looks obviously broken until compared side-by-side with another page. When adding a new top-level page under `app/**/_components/<View>/`, copy the `s.page` wrapper pattern rather than assuming `AppShell`/`AppFrame` supplies it.

- **`ConventionsView`'s candidate list is a persistent checklist, not a processing queue — accepted/rejected cards deliberately stay visible, never filtered out.** `list.map(...)` renders every candidate regardless of `status`; only at "Create skill" time does `acceptedCandidates = list.filter(c => c.status === "accepted")` get pulled out for the modal. This is intentional per `docs/conventions-extractor-plan.md`'s Track 1 description ("approve / reject / edit / re-scan / **deselect-all**") — the "Deselect all" toolbar button bulk-resets every non-pending card back to `pending`, which only makes sense if accepted/rejected cards remain visible and re-toggleable up until you actually generate the skill. Don't add filtering/hiding for accepted or rejected candidates in the main list — that would break the ability to review/reverse decisions via Deselect all (or per-card, by re-clicking Accept/Reject) before finalizing.

- **`activeKeyFor` (`components/app-shell/helpers.ts`) maps ANY pathname containing `/onboarding` to the `onboarding-tour` nav key** (substring `includes`, first match wins) — so the existing `/onboarding` "Add a repository" screen lights up the Onboarding Tour sidebar item. A new repo-scoped page must use a path that can't collide with an earlier `includes()` branch (the tour spec picked `/repos/:repoId/tour`), and the mapping needs fixing alongside it. Also: an unwired onboarding scaffold already exists (feature model `onboarding`, `knowledge.ts` `Onboarding` contract with a mermaid `diagram`, i18n namespace `onboarding`) — check it before adding parallel types (found 2026-10-25, `specs/2026-10-25-onboarding-generator.md`).

- **`repoIdFromPath` (`lib/repo-context.tsx`) treats the first segment after `/repos/` as the active repo id (`/^\/repos\/([^/]+)/`)** — so any static route like `/repos/new` makes the active repo `"new"` (switcher shows "not found", repo-scoped queries hit `/repos/new/...`). Next.js routing itself is fine (static segment beats `[repoId]`); the repo context must exclude reserved segments when adding one (found 2026-10-25 while speccing Add-repo → `/repos/new`).

- **A mutation's `isPending` does not stop two clicks in the same tick from firing two POSTs** — the re-render that disables the button comes too late. Guard with a `useRef` in-flight flag (reset on settle/error), as `useOnboardingResync` in `lib/hooks/onboarding.ts` does; an RTL double-`fireEvent.click` test caught 2 POSTs before the guard (2026-10-25, P-3).
- **2026-11-08 — hooks that expose a typed 409 should resolve only the "attach to existing" case.** `eval_run_in_progress` resolves `{kind:'in_progress', activeRunId}`; every other 409 still rejects so the global MutationCache toast fires. For a same-tick double-click guard share one in-flight promise via `useRef` instead of throwing (a throw triggers the global error toast). To test "invalidate once on terminal status" seed the sibling query keys and assert `getQueryState(key).isInvalidated` instead of counting refetches.
- **2026-11-08 — UI kit gotchas found building the eval components.** `Checkbox` from `@devdigest/ui` has no `disabled` prop — use a native `<input type="checkbox">` for a disabled state (max-two run picker). `Modal` renders two buttons named "Close" (X icon + footer), so tests need `getAllByRole`. `Icon` has no `Pencil`/`GitCompare` — use `Edit`/`Layers`. jsdom has no `scrollIntoView` — call it with `?.`. `useTranslations` renders the raw KEY for a missing message instead of failing, so a missing i18n key shows up only visually in production — list missing keys in the task report. Any test rendering `FindingCard` (even transitively via `FindingsPanel`) now needs a `QueryClientProvider`; `vi.spyOn(api, "post")` with a real `ApiError(msg, 409, code, {reason})` exercises the real reason mapping.
- **2026-11-08 — eval tab/dashboard test + chart gotchas.** The `Tabs` primitive renders plain `<button>`s with no `role="tab"`/`aria-selected`, so assert via `getByRole("button", { name })`. `Sparkline` (`vendor/ui/charts`) divides by `data.length - 1`, so ONE point yields NaN coordinates — callers must draw it only with 2+ points. Editor-tab test recipe: real `QueryClientProvider`, a stubbed `fetch` routed by `URL.pathname`, `vi.mock("next/navigation")` for `useSearchParams`; fake timers need `shouldAdvanceTime: true` and an advance of 2500 ms per 2000 ms poll. On macOS `sed -i` needs `sed -i ''` and bracketed Next.js paths need a non-`/` delimiter — prefer Edit.
- **2026-11-08 — eval trend chart + editor modal (T11).** `DiffViewer`/`FileCard` call `useTranslations("shell")`, so any test rendering them needs the `shell` namespace. Recharts in jsdom has a zero-size `ResponsiveContainer` — test the tooltip body component and a visually-hidden data table, not the SVG. An editor modal that can be saved twice must remember the saved id (pass `existingId` to `onSave`), else "Run case" then "Save" creates a duplicate. `CompareRunsModal` has `footerExtra`/`mode` slots — containers must pass `<PromoteButton/>` themselves.
- **2026-11-08 — Next 15 dashboard route + deep-link editor (T12/T13).** A view that calls `useSearchParams` needs `<Suspense>` in its `page.tsx`. A route-level `error.tsx` at `app/eval/` already covers child segments (no copy per child route). Native `<select>`s for period/agent selectors keep RTL tests simple (`fireEvent.change`). To drive `?case=` and a New/Edit editor from one place, derive the open case during render from (explicit editor state ?? deep-link param unless dismissed) — no `useEffect` sync-state. The Evals-tab trend/sparklines use the dashboard's default 30-day window while the tiles use all runs. Don't `sed -i` paths containing `[id]` — use Edit.
- **2026-11-08 — skill-mode eval client (T16).** Calling `api.post(path, undefined)` breaks `toHaveBeenCalledWith(path)` assertions elsewhere (it records a second `undefined` argument) — call `api.post(path)` with NO second argument when there is no body. Skill runs reuse `EvalSuiteRun.agent_id` as the host agent and `host_agent_name` for display; `CompareRunsModal mode="skill"` diffs `skill_body` and warns when the two runs used different host agents.
- **2026-11-08 — skill Evals tab + FindingCard target menu (T17/T18).** When host/run state is shared by a header button and a tab, lift it into a keyed wrapper (`SkillEditor` → `SkillEditorBody key={skill.id}`) instead of `useEffect` resets. `RunEvalNotice` has no `no_host_agent` variant, so skill-side code widens the type locally. Rendering the full `SkillEditor` in tests needs `@/lib/repo-context` mocked (`ContextTab` imports it). The FindingCard targets query is gated by passing a `null` id to `useEvalTargets`, so undecided cards never fetch. ## Tool & Library Notes

- **Evenly-spaced round dotted underline** (severity-coloured leader under the findings badges) is a `radial-gradient(circle, COLOR 1.1px, transparent 1.6px)` with `backgroundSize: "5px 2px"`, `backgroundRepeat: "repeat-x"`, `backgroundPosition: "left bottom"` — NOT `border-bottom: dotted`, whose dots render as chunky touching squares. Set `background: transparent` first (bare badge) then the gradient via `backgroundImage` (later key wins over the shorthand's image reset). See `SeverityBadge underline` in `vendor/ui/primitives/Badge.tsx`.

- **`Icon` names are the map keys in `vendor/ui/icons.tsx`, NOT the raw lucide export names.** The map aliases some: e.g. `Edit: Pencil` — so the valid `IconName` is `"Edit"`, and `<Badge icon="Pencil">` fails typecheck (`TS2322`). When picking an icon, grep the object keys in `icons.tsx` (the `satisfies Record<string, LucideIcon>` block) rather than assuming lucide's name is exported.

- **`Donut` (`vendor/ui/charts/Donut.tsx`) defaults its legend to a dollar amount** (`${valuePrefix}${n.toFixed(2)}`, `valuePrefix="$"`). For integer/count legends (e.g. findings-by-category), pass `format={(n) => String(n)}` — a `format?: (n:number)=>string` prop overrides the money formatting without touching existing cost callers.

- **`Button`'s `active` prop only has a visual effect for `kind="tertiary"`** (`vendor/ui/primitives/Button.tsx`) — the `secondary`, `ghost`, `primary`, and `danger` style maps never read `active` at all, so `<Button kind="secondary" active={someBoolean}>` silently renders identically whether `someBoolean` is true or false. `ConventionCandidateCard`'s Accept/Reject buttons passed `active={accepted}`/`active={rejected}` with `kind="secondary"`/`kind="ghost"` and had zero visual state feedback as a result (only the card's left border color changed). Fix is to switch `kind` itself based on state (e.g. `kind={accepted ? "primary" : "secondary"}`) rather than relying on `active` — or extend the style maps if you actually want `active` to do something for those kinds.

- **`ConventionCandidateCard`'s Accept/Reject buttons are intentionally asymmetric in color, not a leftover bug.** Accept escalates to `kind="primary"` when `accepted` (the only kind with a filled `var(--accent)`/blue background per `Button.tsx`'s style map), while Reject only ever toggles between `"ghost"` (not rejected) and `"secondary"` (rejected) — it never reaches `"primary"`, so it never gets a colored fill, only a neutral gray outline/fill. Don't "fix" Reject to also turn blue when accepted-style-symmetry looks broken — Accept is deliberately the only button that carries the accent color, since it's the path toward the primary next action (bundling into a skill); Reject is modeled as a neutral/muted state. (The card's left border, separately, is always `var(--ok)` green regardless of status — see the entry below — only `opacity` in `styles.ts#card(rejected)` changes with status.)

- **TanStack Query v5: a DISABLED query (`enabled: false`) sits in `status: 'pending'` forever — gate loading UI on `isLoading`, not `isPending`.** `useQuery({ enabled: prId != null })` never runs while disabled, so `isPending` stays `true` indefinitely (there's no cached data). A component doing `const loading = query.isPending` then renders its skeleton FOREVER whenever the query is disabled — the exact `prId === null` case an `enabled` guard is written to handle. Use `isLoading` (v5 = `isPending && isFetching`), which is `false` for a disabled query. Also relevant for mutations: don't fold `mutation.isPending` into the same body-`loading` flag or a re-fetch/recompute wipes the currently-shown data — let the trigger button show its own `loading` spinner instead (see `IntentPanel.tsx`).
- **Add-repo screen now lives at `/repos/new`; `/onboarding` is a server-component redirect (2026-10-25).** `repoIdFromPath` (exported, `lib/repo-context.tsx`) returns `null` for reserved first segments (`new`) so the shell never fetches `/repos/new/...` as a repo id, and `activeKeyFor` matches `onboarding-tour` only on `/repos/<id>/onboarding` (regex excludes `new`). Supersedes the 2026-10-25 note that `/onboarding` lights up the tour nav item. Any new static `/repos/<segment>` route must be added to `RESERVED_REPO_SEGMENTS`.
- **2026-10-25 — Onboarding tour sections:** `rerender()` from `renderWithIntl` drops the `NextIntlClientProvider` wrapper (rerender renders the bare element) → `unmount()` and render again. A helper returning RTL's `render` needs an explicit `RenderResult` return type (TS2742 under pnpm). Container query for the first-tasks grid is Tailwind 4 `@container` + `@[720px]:grid-cols-3` (works in this repo; no other component uses Tailwind classes yet, rest is inline `styles.ts`).
- **2026-11-08 — Checking the UI against a "standalone" design HTML (`DevDigest Design (standalone).html`).** It is a bundler file: `<script type="__bundler/manifest">` holds base64 (+gzip when `compressed`) assets — the screens are plain `React.createElement` JS (`screen_skills.jsx` → `ScreenEval`, `screen_cizruns.jsx` → `ScreenEvalCase`), readable as source for exact styles/copy. To get pixel references, open the file in `agent-browser` (use a separate `AGENT_BROWSER_SESSION`), then per artboard `document.querySelector('[data-dc-slot="<id>"]').scrollIntoView({block:'start',inline:'start'})` + `set viewport 1280 1000` + `screenshot`; artboards aren't addressable by `id`/`--selector`. Compare against our pages at the same viewport.

## Recurring Errors & Fixes

- **2026-10-25 — RTL: `mutation.mutate()` calls `mutationFn` in a microtask, so `expect(post).toHaveBeenCalledTimes(1)` right after `fireEvent.click` sees 0.** `await screen.findBy…` (the disabled/"Generating…" button) first, then assert the call count. Colocated tests importing `messages/en/*.json` need one `../` per directory level to `client/` (OverviewTab/IntentPanel are 8, PrBrief subfolders 9). `renderHook` tests that mock `../api` as `{ api }` must spread `vi.importActual` if the hook imports `ApiError`.

- **2026-10-19 — Resync "completes" instantly if started before index-state has loaded.** The baseline `updatedAt` is `undefined`, so the first refetch (`old !== undefined`) looks like completion and the stale degraded map is refetched. Gate start on a loaded baseline (`useBlastResync().canStart`; Resync button disabled until then). Test such TanStack polling hooks with `renderHook` + a real `QueryClient`, `vi.mock('../api')`, `vi.useFakeTimers()` and `await act(() => vi.advanceTimersByTimeAsync(ms))`.

- **2026-10-19 — There is no `--text` CSS variable; use `--text-primary` (also `--text-secondary`, `--text-muted`).** An undefined `var(--text)` in an SVG `fill` silently falls back to black, so the BlastGraph node labels were invisible on the dark theme while tests stayed green (jsdom doesn't resolve CSS vars). Before using a token, check it exists in `src/vendor/ui/styles.css` (`--accent-fg` doesn't either — always give it a fallback).

- **A skills mutation that creates a NEW version must invalidate `["skill-versions", id]`, not just `["skills"]` / `["skill", id]`.** `useUpdateSkill` invalidates only the latter two, so after a body change (which bumps the version and snapshots a new `skill_versions` row) the Versions tab's `useSkillVersions` query stays stale until some unrelated refetch. The dedicated `useRestoreSkill` (restore always creates a version) adds the `["skill-versions", data.id]` invalidation — mirror that in any future mutation that can change `body`. Restore itself is now a real server endpoint (`POST /skills/:id/restore`), not the old client-side workaround of re-PUTting the old body via `useUpdateSkill`.

- **`GET/POST /agents/:id/skills` returns bare `AgentSkillLink` rows (`{ agent_id, skill_id, order }`), NOT a joined `{ skill: Skill, order }`.** It's easy to assume otherwise because the server-side `AgentsRepository.linkedSkills()` *does* return a joined `LinkedSkillRow` (`{skill, order}`) — but the route (`agents/routes.ts`) calls `service.skillLinks()`, which maps to the public `AgentSkillLink` DTO (already in `@devdigest/shared`), i.e. ids only. A mocked-fetch hook test using the wrong (joined) shape will pass green while the real endpoint silently returns `undefined` for `.skill.id`/`.skill.enabled` at runtime — caught only by hitting the live API (`curl localhost:3001/agents/:id/skills`), not by typecheck or the component's own RTL test. If you need the full `Skill` for a link row, look it up by `skill_id` against an already-fetched skill list (e.g. `useSkills()`) — see `SkillsTab.tsx`'s `byId` map.

- **`pnpm dev` "starts fine" on :3000 even when another dev server already holds `[::1]:3000` — and `localhost:3000` then serves the OTHER app.** Next binds the wildcard `*:3000`, which does not collide (no `EADDRINUSE`) with a process bound specifically to IPv6 loopback (seen: an Nx dev server from another project). macOS resolves `localhost` to `::1` first, so the browser/`curl localhost:3000` hit the other app (blank `<title>`), while `127.0.0.1:3000` serves DevDigest. Diagnose with `lsof -nP -iTCP:3000 -sTCP:LISTEN` (two listeners = shadowed) and compare `<title>` on `127.0.0.1` vs `localhost`. Fix: stop the other process, or use `http://127.0.0.1:3000`.

- **2026-10-25 — A long-running `next dev` can hang: it still holds :3000 (one healthy-looking `lsof` listener) but every request times out.** "Is it running?" is not answered by `lsof`/`ps` — probe it: `curl -s -o /dev/null -w '%{http_code}' --max-time 30 http://localhost:3000/` (`000` after the timeout = hung). ### 2026-07-08 — Clickable Smart Diff severity chips → deep-link to a finding in "Agent runs"
- **A URL-param cannot make a `FindingCard` "expand itself on mount" — the card isn't mounted.** The findings tab nests `FindingsTab → ReviewRunAccordion (own `open` state, collapsed by default except index 0) → FindingsPanel → FindingCard`. A FindingCard inside a collapsed accordion is not in the DOM, so any "read `?finding` on mount and expand" logic never runs for it. Deep-linking to a finding must therefore drive the *whole chain*: `ReviewRunAccordion` opens if `review.findings.some(f => f.id === target)`, then `FindingCard` expands + `scrollIntoView` via an effect keyed on the target. Mirrors the existing Timeline→Review-run `targetRunId`/`targetNonce`+effect pattern (`ReviewRunAccordion.tsx:47`) rather than inventing a new mechanism.
- **`FindingsPanel`'s "hide low confidence" toggle can delete the navigation target from the DOM.** `shown = visibleFindings(findings, hideLow)` filters before mapping to cards, so deep-linking to a SUGGESTION/low-confidence finding while `hideLow` is on scrolls to nothing. Fix applied: when the target exists in `findings` but not in `shown`, `setHideLow(false)` first, then focus it. Any future "navigate to item X in a filtered list" needs the same guard — reveal before scroll.
- **The severity chip is rendered in `CodeLine` but its finding identity is dropped one layer up.** `FileCard.severityByLine()` collapsed findings to `Map<lineNo, Severity>` (highest-severity-wins), discarding `f.id`. To make the chip a link it now carries `{severity, findingId}` (the *winning* finding's id). `CodeLine`/`FileCard` are shared with the plain `DiffViewer`, so the click is opt-in via an `onFindingClick?` prop (plain viewer passes none → chip stays a static `<span>`), and no `useTranslations` was added there (aria-label is a hardcoded string, matching the existing "Add a comment on this line" label) — keeps the shared components locale-agnostic per the FileCard rule above.
- **React treats `borderColor` (and `borderWidth`) as SHORTHANDS relative to `borderLeftColor`/`borderLeftWidth` — being "mostly longhand" isn't enough.** `FindingCard/styles.ts`'s `s.card` was written with an explicit comment claiming it avoided the shorthand/longhand mix, yet it paired `borderColor` with `borderLeftColor` (and `borderWidth` with `borderLeftWidth`). React only fires the "Updating a style property during rerender (borderColor) when a conflicting property is set (borderLeftColor)" warning when the shorthand member actually *changes between renders* — here when `focused` toggles the border color — which is why it stayed silent until a feature (Smart Diff chip deep-link) started flipping `focused` on navigation. Fix: go FULLY per-side (`borderTop/Right/Bottom/LeftColor` + matching `...Width`), never `borderColor`/`borderWidth` alongside a `borderLeft*`. A latent version of this can hide in any card/row style that has a colored left-accent border plus a focus/hover color change. Caught only in the browser console (screenshot from the user) — jsdom/vitest doesn't surface it, so component tests stayed green through the bug.

### 2026-07-09 — `useEffect` that calls its own `setState` cancels its own cleanup timer (FileCard highlight never fades)
- **`FileCard.tsx`'s finding-scroll effect sets a 1500ms `setTimeout` to restore the row background, then calls `setPendingScrollLine(null)` in the same effect body — but `pendingScrollLine` is in the effect's dep array, so that state write re-invalidates the effect and React runs its cleanup (`clearTimeout`) on the very next render, cancelling the restore.** Net result: the "transient" highlight applied via direct DOM mutation (`el.style.backgroundColor = 'var(--accent-bg)'`) is never removed and stays for the life of the card. Compounded by the fact that the highlight is written on the outer `rowWrap` div, whose React `style` prop (`cs.rowWrap`, a stable const) never sets `backgroundColor`, so React never overwrites it either. Surfaced by the pr-self-review react lens (conf 85); it's pre-existing base smart-diff code, not the clickable-badge change. Fix pattern: don't reset the trigger state inside the same effect — track "consumed" via a `useRef`, or do the reset inside the `setTimeout` callback after restoring styles, so the effect isn't torn down by its own write. General rule: an effect must not `setState` on a value it depends on unless it wants to re-run + re-clean-up itself.
