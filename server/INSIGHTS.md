# server — INSIGHTS

Append-only log of decisions, gotchas discovered, and lessons for the API package.
Newest first. Capture what wasn't obvious from the code — the "why" behind a choice,
or a trap someone hit — so the next person (or agent) doesn't relearn it.

## What Works

- **`ReviewOutcome.costUsd` is the actual OpenRouter charge** — `reviewer-core/src/llm/openrouter.ts` extracts `usage.cost` from the API response and accumulates it across chunks. Always prefer this over `priceBook.estimate()` which uses static list prices and can be 15–35% off from the actual billed amount due to dynamic provider routing.

## What Doesn't Work

- **`priceBook.estimate()` for displayed cost** — Uses `/models` list price; OpenRouter routes dynamically (DigitalOcean, Cloudflare, Alibaba) with different prices per provider, plus caching discounts. Don't use as a display value — use only as a fallback when `costUsd` is null (old rows before the `cost_usd` DB column was added).

## What Doesn't Work

- **Splitting parallel agent work by file ownership isn't enough when tasks share global runtime state.** Building the Skills feature, one parallel task owned `server/src/modules/skills/**` (its own integration tests) and a separate task owned `server/src/db/seed.ts`/`seed-prompts.ts` (adding the seed data). They looked file-disjoint, but EVERY `*.it.test.ts` calls `seed()` in `beforeAll` — so the skills-module task's tests transitively depended on `seed.ts` being valid, and both tasks ended up editing `seed.ts`/`seed-prompts.ts` concurrently to unblock their own test runs. It resolved fine this time (final state was consistent, verified by rerunning typecheck + all test suites), but it was luck of write-order, not design. When splitting work across agents/sessions in this repo, treat `seed.ts` as a shared resource requiring sequencing, not something safe to touch from two lanes at once just because the primary target files differ.

## Codebase Patterns

- **repo-intel indexes only JS/TS (`SUPPORTED_EXT` in `modules/repo-intel/constants.ts`) and caps at `MAX_INDEXED_FILES = 5000`.** So the index file list is NOT "all files in the repo": Markdown/specs/config/other-language files are invisible to it, and "files indexed" undercounts big repos. A feature that grounds arbitrary repo paths (e.g. onboarding first-task paths like `specs/`) needs the tracked-file list at the commit, not the index; any UI count should show the real `files_indexed` (found 2026-10-25, onboarding spec).

- **`JobRunner` (`platform/jobs.ts`) wraps every handler in `withRetry(retries: 2)` + its own 120 s `withTimeout`, on a shared concurrency-3 queue** — a handler that throws after an LLM call re-runs the LLM call up to 2 more times (a "1 LLM call per job" budget silently becomes 3, and wall time up to ~3×timeout). For LLM-backed jobs, make the handler never throw: catch everything, apply your own timeout, and persist `failed/<reason>` yourself (found 2026-10-25 planning the onboarding tour).
- **repo-intel's `readClone(clonePath, file)` has no realpath/symlink confinement; `container.git.readFile` does** (`adapters/git/simple-git.ts`). Read clone files for prompts through `git.readFile`. The repo-intel facade also takes only `repoId` — check workspace ownership of the repo before calling it (found 2026-10-25, onboarding plan review).

- **A job handler's own timeout must be strictly shorter than `JobRunner`'s 120 s `withTimeout`, or the runner wins the race.** With both at 120 s the runner's timer (started first) rejects `job.done` with `TimeoutError` (not retryable), the caller's `.catch` writes `failed/internal`, and the handler's own `failed/timeout` write is superseded. Onboarding fix: clamp `onboardingTimeoutMs` to `ONBOARDING_TIMEOUT_CEILING_MS = 110_000` in `platform/config.ts` and map a runner `TimeoutError` to `timeout` in `job.done.catch` (2026-10-25 fix loop, P-1).
- **Zod `.max(n)` on strings counts UTF-16 code units, not code points.** A cap implemented with `Array.from(s).length` lets emoji/astral text through, and the later `Contract.parse` throws — discarding a valid result. Count with `.length` and never cut between a surrogate pair (see `cutText` in `modules/onboarding/limits.ts`) (2026-10-25, P-2).

- **2026-10-25 — A background job's deadline and the read-side "overdue" check must run on ONE clock (the claim time).** Onboarding GET expired `generating` rows at `generation_started_at + timeout + 30s grace` (claim time), but `runGeneration` started its own `withTimeout` only when the handler ran. Because onboarding shares the concurrency-3 `JobRunner` queue with clone/index jobs (up to 120 s each), a queue wait over 30 s let a GET mark a LIVE run `failed/timeout`. That reopened single-flight, so a second generation and a second LLM call could start, and the first tour was dropped as `superseded`. Fix: compute the job deadline from the row's `generationStartedAt` (`job.ts`), so queue time counts against the budget. Test: `onboarding/job.test.ts`.

- **`withTimeout(p, ms)` (`platform/resilience.ts`) with `ms <= 0` returns `p` UNTIMED; it does not time out immediately.** Code that computes a remaining budget (`deadline - Date.now()`) must handle `remaining <= 0` itself (throw `TimeoutError`), or an already-expired job runs with no timeout at all.

- **LLM-proposed shell commands shown with a copy button must be grounded against shell syntax, not just against the manifest.** `onboarding/commands.ts` split steps only on `&&` and kept any unknown head, so a prompt injection in the repo's README could produce `pnpm install; curl … | sh` or `rm -rf ~` that passed grounding. It now drops `; | & \` < > $(` (only `&&` allowed) and a denylist of heads (`rm`, `sudo`, `curl`, `wget`, `sh`, `bash`, `eval`…). Apply the same rule to any future "runnable text from the model" feature.

## Tool & Library Notes

- `ONBOARDING_TIMEOUT_MS` uses `z.preprocess('' -> undefined)` before `z.coerce.number()`: a bare empty env var would coerce to `0` and fail `.positive()`. Same trick as `LOG_LEVEL`. (Onboarding T1, 2026-10-25)
- `GitClient.listTrackedFiles` must keep `-z` on `git ls-tree`: without it git C-quotes non-ASCII paths (`"\320\264..."`) and exact-match grounding silently fails. The sha is regex-validated before reaching git so it can never parse as an option. The client `vendor/shared/adapters.ts` `GitClient` copy lacks `sync`/`diffNameOnly`, so add new port methods at that copy's own anchor. (Onboarding T1, 2026-10-25)

- **fflate `unzipSync` — enumerate before you inflate (decompression-bomb defense).** The `filter` callback runs per entry BEFORE decompression and receives `{ name, size, originalSize, compression }`, where `originalSize` is the uncompressed size from the zip header. Returning `false` skips inflating that entry entirely. So the safe pattern for reading one file out of an untrusted `.zip` (see `modules/skills/helpers.ts`) is TWO passes: pass 1 `filter: () => { infos.push(...); return false }` collects names + declared sizes with zero inflation → cap entry-count and the target's `originalSize`; pass 2 `filter: (f) => f.name === target` inflates only the chosen entry. A lying (understated) size header can't slip past — fflate allocates `out` to the declared size and errors mid-inflate when the stream overruns it, so a `try/catch` at the caller still bounds it. Don't call bare `unzipSync(buf)`: it eagerly inflates ALL entries into memory synchronously and blocks the event loop.

- **`UnifiedDiff.files[]` has NO raw per-file `.patch` string** (`vendor/shared/adapters.ts:185`) — `parseUnifiedDiff` (`adapters/git/diff-parser.ts`) already breaks each file into structured `DiffHunk[]` (`oldStart/oldLines/newStart/newLines/newLineNumbers`), discarding the raw `@@ ... @@` text. The raw `.patch` string only exists one layer down, on the `pr_files` DB row, consumed solely by `diff-loader.ts`'s reconstruction fallback (`diffFromPrFiles`) when no real clone is available. If you need `@@ -a,b +c,d @@` header text from an already-loaded `UnifiedDiff` (e.g. `modules/intent/signals.ts#hunkHeaders`, built for the cheap-signals PR-intent classifier), reconstruct it from the structured hunk fields — `` `@@ -${h.oldStart},${h.oldLines} +${h.newStart},${h.newLines} @@` `` — don't look for a patch substring to slice, it isn't there.

- **New optional fields on the `PromptAssembly` contract (`vendor/shared/contracts/trace.ts`) must be `.nullish()`, not `.nullable()`.** `PromptAssembly` has two constructors: `assemblePrompt` in `reviewer-core/src/prompt.ts` (sets every field, so it doesn't care) and `emptyPromptAssembly()` in `server/src/platform/trace-builder.ts`, which builds a literal that OMITS the optional fields (`callers`/`repo_map`/`pr_description`/`intent`). A `.nullable()` field is still a *required* key in the inferred TS type, so adding one silently breaks `emptyPromptAssembly()`'s literal at typecheck; `.nullish()` (optional + nullable) keeps that constructor compiling untouched. Confirmed while adding `intent` for the Intent Layer's `## Intent` prompt section — mirror the change in BOTH the server and `client/src/vendor/shared/contracts/trace.ts` copies (byte-for-byte identical).

## Tool & Library Notes

- **`node:net`'s `BlockList` conflates address families when mixed rules share one instance.** A single `BlockList` that has BOTH a plain IPv4 subnet (`addSubnet('10.0.0.0', 8, 'ipv4')`) AND the IPv4-mapped IPv6 subnet `::ffff:0:0/96` (`addSubnet('::ffff:0:0', 96, 'ipv6')`) makes `check(anyPublicIpv4Address, 'ipv4')` return `true` for literally EVERY IPv4 address, not just ones in the listed ranges — confirmed reproducibly on Node 22.23.1 with a throwaway `node -e` (`93.184.216.34` came back blocked even with no matching v4 rule). Node evidently normalizes an IPv4 check against the IPv4-mapped-IPv6 form too, so it collides with any `::ffff:0:0/96`-style v6 rule. Fix: use TWO separate `BlockList` instances — one with only `'ipv4'`-typed rules, checked with `.check(ip, 'ipv4')` for `net.isIP(ip) === 4`; another with only `'ipv6'`-typed rules (including `::ffff:0:0/96` to catch IPv4-mapped IPv6 literals), checked with `.check(ip, 'ipv6')` for `net.isIP(ip) === 6`. See `adapters/http/web-fetch.ts` (`buildV4BlockList`/`buildV6BlockList`). Always verify a `BlockList`-based guard with a `node -e` sanity script covering a real public IP before trusting it — this bug fails in the "blocks too much" direction (which looks safe but silently breaks the feature), the opposite failure mode from the fail-open regex bug it replaced.
- **The deprecated IPv4-COMPATIBLE IPv6 form `::a.b.c.d` (e.g. `::127.0.0.1`) is a distinct address space from the IPv4-MAPPED form `::ffff:a.b.c.d`.** Only `::/96` (all top 96 bits zero) catches the compat form; `::ffff:0:0/96` does not (its 80-95 bit group is `ffff`, not `0`). `::/96` also happens to cover the unspecified address `::` itself (`0:0:0:0:0:0:0:0` has all 96+ bits zero), so adding it closes both the `::` bypass and the `::a.b.c.d` bypass in one rule — needed both in the SSRF guard's IPv6 `BlockList`.
- **`vitest related <file> --run` ignores the unit/integration split — always add `--exclude '**/*.it.test.ts'`.** `related` walks the import graph and happily picks up Docker-backed `*.it.test.ts` files: `related src/modules/settings/constants.ts` took ~54s and failed (testcontainers) without the exclude vs ~1.3s / 6 green tests with it (vitest 2.1.9, 2026-10-21). Also: `related` on a file no test imports prints "No test files found" and exits **0** — that is not a pass. This is the targeted-test command `implementer` uses inside `/run-plan`, so keep the exclude in any copy of it.

- **Onboarding grounding core (`modules/onboarding/{paths,ground,commands,inputs,deterministic,limits}.ts`) is pure; a ref `dir/*` or `dir/**` means "anything under dir".** `path.posix.matchesGlob('src/api/public/index.ts', 'src/api/*')` is `false` (single-segment `*`), but the spec's AC-18 wants `src/api/*` kept when only a nested file is indexed. `PathIndex.matchesRef` therefore answers `/*` and `/**` with `hasDir(prefix)` and only uses `matchesGlob` for `dir/*.ext`; any `{` is rejected (brace-expansion DoS). Run-step grounding (`groundRunStep`) validates each `&&` segment, tracking `cd <dir>` to pick the right `package.json`/Makefile; a manifest not read (cap 10) means the script can't be verified, so the step is dropped. (Onboarding T3, 2026-10-25)
- **`wrapUntrusted` only escapes `</untrusted>`; label attribute is not escaped.** Any repo-derived string used in a label (file path, repo name) must be sanitised first (`["<>\r\n]` -> `_`, see `safeLabel` in `onboarding/inputs.ts`), otherwise a crafted file name breaks out of `source="…"`. Also keep trusted instructions before the "everything inside <untrusted> is DATA" sentence and assert ordering in tests with `indexOf('<untrusted source=')`, because the sentence itself mentions `<untrusted>`. (Onboarding T3, 2026-10-25)

- **Onboarding job lifecycle (`modules/onboarding/{job,service,repository}.ts`): the handler must never throw, and must be idempotent against JobRunner retries.** `JobRunner` retries a throwing/timed-out handler 2x, which would re-call the LLM (NFR-5). So `runGeneration` catches everything, wraps its body in its own `withTimeout(config.onboardingTimeoutMs)`, writes `failed/<reason>` itself, and bails out early when the row's `generation_id`/`generating` status no longer match or the id is already in the module-level `running` Set (JobRunner's own 120s timeout can fire first and re-enter the handler while the first run is still alive). All terminal writes are `UPDATE ... WHERE repo_id AND generation_id AND generation_status='generating'`, so a zombie completion can't overwrite newer state. Single-flight is one atomic `INSERT ... ON CONFLICT (repo_id) DO UPDATE SET ... WHERE generation_status IS DISTINCT FROM 'generating' RETURNING` (Drizzle `setWhere`); no row back = someone else is generating. (Onboarding T5, 2026-10-25)
- **The boot reaper lives in the onboarding plugin (`reapOnBoot()` at registration), so every `buildApp()` on the same DB reaps ALL `generating` rows.** In it-tests that build several apps per file, await each generation to a terminal state before building the next app, or the new app marks the in-flight row `failed/interrupted`. It is also what AC-15's test relies on (insert an old `generating` row, build an app, GET). (Onboarding T5, 2026-10-25)
- **Spy on `app.log` to assert structured logs in it-tests.** `buildApp` with `LOG_LEVEL=silent` gives an abstract logger, and pino's real destination writes via `fs.writeSync` so `process.stdout.write` spies see nothing. Services therefore take `logger: () => app.log` (resolved per call) and tests do `vi.spyOn(app.log, 'info')`. Always `vi.restoreAllMocks()` in `afterEach`; the silent logger object is shared across apps. (Onboarding T5, 2026-10-25)
- **No repo-intel facade counts `file_edges`; the "no import graph" signal (EC-5) is derived** as: `getCriticalPaths` empty AND no top-ranked file has a fan-in > 0 (`getFanIn`). If a future task needs the exact edge count, add a facade method rather than querying `file_edges` from the onboarding module. Also `MockLLMProvider` can't throw/hang, so it-tests use the inline `StubLLM` in `test/helpers/onboarding-fixture.ts` (modes ok/throw/never/gate). With no `llm.openrouter` override, ALWAYS also override `secrets` with `new MockSecretsProvider({})` or a developer's real `OPENROUTER_API_KEY` leaks into the "no key" test. (Onboarding T5, 2026-10-25)
- **2026-11-08 — drizzle-kit 0.30 / drizzle-orm 0.38 emit correct partial unique indexes and DESC index columns.** `uniqueIndex(...).on(...).where(sql`...`)` and `index().on(t.col.desc())` in `db/schema/eval.ts` generated `CREATE UNIQUE INDEX … WHERE …` and `… DESC NULLS LAST` in migration `0015`. Use a partial unique index to enforce "one active row per owner" atomically (`eval_suite_runs_one_running_uniq`) instead of check-then-insert in service code.

## Recurring Errors & Fixes

- **`vendor/shared` server/client copies were ALREADY not byte-identical before Project Context** (`adapters.ts` lacks `CommitFile*`/`sessionId`/`openrouter`, and `trace.ts`/`knowledge.ts`/`eval-ci.ts`/`productionize.ts` differ in comments or content), so `diff -r` is never clean. Mirror your additions by editing each copy at its own anchor — `git apply` of the server patch onto the client file landed the `RepoDocsStore` block INSIDE a doc comment in client `adapters.ts` (client typecheck broke with TS1005). Verify with a targeted diff of just your block, then `pnpm typecheck` in client. Also: a runtime class (`RepoDocsError`) exported from `shared/adapters.ts` must be imported as a value (`import { RepoDocsError }`), not in an `import type {…}` list, or `new RepoDocsError()` fails TS1361.

- **2026-10-19 — Changing a `FEATURE_MODELS` default silently broke `test/settings-models.it.test.ts`.** hw-3 moved `risk_brief` to `openrouter/deepseek-v4-flash` but the it-test hard-coded `openai/gpt-4.1`; it only surfaced on the next PR because the path-filtered `server-integration` workflow hadn't run on this fork before. The test now reads the default from `FEATURE_MODELS`. When touching registry defaults, run `pnpm exec vitest run .it.test` locally (Docker) — unit tests don't cover it.

- **2026-10-19 — `GitHubClient.getPullRequest` is ~3 GitHub requests (pulls.get + listFiles + listCommits), and `GitClient.log(repo, path?)` has no maxCount/first-parent option.** Read paths that only need title/author/body (pr-history enrichment) must bound and parallelize calls (`Promise.allSettled`, `MAX_GITHUB_ENRICH=3`) and cache per service instance (`${repoId}:${n}`, 10-min TTL); `MAX_LOG_SCAN` only slices after the full log is read — a port change is needed to scan less.

- **Committing a shared file that's already dirty with unrelated uncommitted work sweeps that work into your commit too** — `git add <path>` (even a pathspec-limited `git commit -- <path>`) stages/commits the file's WHOLE current diff, not just the hunk you just typed. Hit this 3× building the Conventions Extractor on a branch that also had a separate, unfinished "skills" feature sitting uncommitted in the same working tree: `server/src/modules/index.ts` and `server/src/db/rows.ts` already had uncommitted skills-module registration lines before the conventions task touched them (client's `nav.ts` had the identical problem — see `client/INSIGHTS.md`). Fix pattern: `git show HEAD:path/to/file > /tmp/clean.ts`, hand-edit `/tmp/clean.ts` to add ONLY your change on top of real HEAD content, `cp /tmp/clean.ts path/to/file && git add path/to/file` and commit that — then re-apply your original full edit (your change + the pre-existing WIP together) to the working tree afterward, uncommitted, so `git diff HEAD -- path/to/file` shows only the pre-existing WIP residual and the file stays fully correct for local testing. Verify with `git show --stat <commit>`, not just `git status` after the fact; `git reset --soft HEAD~1` + redo is the recovery move if caught late.

- **Cleaner than the `/tmp` cp-back dance above: stage a hand-built blob into the index and DON'T touch the working tree.** When a shared file (`modules/index.ts`, client `hooks/index.ts`) has BOTH your change and unrelated WIP lines you must exclude, pathspec can't help (it stages the whole file). Instead: `grep -vxF -e '<wip line>' … path > "$SCRATCH/staged"` (keep yours + HEAD, drop the WIP lines) → `blob=$(git hash-object -w "$SCRATCH/staged")` → `git update-index --cacheinfo 100644,$blob,path`. This puts your scoped content in the index while the working file keeps its WIP for local dev — then commit with a **BARE `git commit`** (a pathspec here would re-stage the full working file and undo the surgery; this is the one case bare-commit is correct — you curated the index by hand, so first confirm `git diff --cached` shows only your lines and nothing else is staged). Used to land the Smart Diff registration lines in `modules/index.ts` while leaving the uncommitted Intent-Layer `intent,` line out (2026-07-08). Don't wrap this in a bash *function* in the Bash tool — the zsh wrapper lost PATH/`mktemp` mid-function; inline the commands.

- **A `FeatureModelId` registry entry can default to a provider you have no key for.** `FEATURE_MODELS` (`vendor/shared/contracts/platform.ts`) hardcodes a default `provider`/`model` per feature — e.g. `conventions` → `openai`/`gpt-5.4` — independent of what's actually in `~/.devdigest/secrets.json`. A partial local setup may only have `OPENROUTER_API_KEY`, so calling an unoverridden feature fails at call time with `{"error":{"code":"config_error","message":"OPENAI_API_KEY is not configured"}}`. Fix: `PUT /settings` with `{"feature_models": {"<id>": {"provider": "openrouter", "model": "<a real openrouter model>"}}}` before exercising that feature. Resolution goes through `resolveFeatureModel(container, workspaceId, id)` (`modules/settings/feature-models.ts`), which falls back to the registry default only when no override row exists. A `routeModel(...)` helper is referenced in at least one planning doc (`docs/conventions-extractor-plan.md`) but does **not exist** in this codebase.

- **A new `NOT NULL text` column with no `DEFAULT` on an existing table breaks the migration the moment the table has any rows** — drizzle-kit happily generates a bare `ALTER TABLE ... ADD COLUMN category text NOT NULL` (no default) if the schema field is `text('category').notNull()` with nothing else; it applies fine against an empty dev table but fails on any environment where the table is already seeded. `status` on the same table shipped correctly (`.notNull().default('pending')`) — always add a `.default(...)` (or split into add-nullable → backfill → set-not-null across migrations) for any `NOT NULL` column added to a table that might already have rows.

- **API serving stale code despite edits → check for duplicate `tsx watch src/server.ts` processes.** Multiple `pnpm dev` instances can accumulate; only one binds `:3001` and the others' children may keep serving OLD code (or a killed watcher leaves an orphaned child on the port). Symptom: a route change has no effect even though the file on disk is correct. Fix: `lsof -nP -iTCP:3001 -sTCP:LISTEN` to find the real owner, `kill` all `tsx watch` parents + the listening child, confirm `:3001` is free, then start one fresh `pnpm dev`.

- **`docker exec devdigest-postgres psql -U postgres …` fails with `FATAL: role "postgres" does not exist`.** The container has no default superuser role — the DB and role are both `devdigest` (see `DATABASE_URL` in `server/.env` / `docker-compose.yml`). Use `psql -U devdigest -d devdigest`. Useful for ad-hoc checks like confirming an applied migration: `select id, created_at from drizzle.__drizzle_migrations order by id desc;`.

- **`waitForPrRuns` returns before the run trace exists.** `completeAgentRun` flips `agent_runs.status` to `done` *before* `saveRunTrace`, so a `GET /runs/:id/trace` right after the wait can 404/return a partial doc (flaky `specs_read === undefined`). In integration tests poll the trace endpoint until the expected field appears (see `test/run-executor-project-context.it.test.ts#run`). Also: a second review run on the same PR needs `waitForPrRuns(..., { expected: priorRuns + 1 })`, otherwise the first terminal run satisfies the wait immediately.

- **2026-10-25 — `column <table>.<col> does not exist` (500 → client toast) mid-branch = a newly generated migration isn't applied yet.** The API boots and `/health` is fine; only routes touching the new columns fail (seen: onboarding page, `onboarding.generation_status` from `0014_*`). Its output dumps multi-line Postgres objects ending in `routine: 'transformCreateStmt'`, which look like errors but are `severity: 'NOTICE'` ("extension vector / schema drizzle already exists, skipping"). The real success signal is the final `✓ migrations applied`.

## Codebase Patterns

- **For a "free"/token-free feature that composes existing PR data, read `pr_files` via `container.reviewRepo.getPrFiles(prId)` — NOT the `GET /pulls/:id` detail path.** The pulls detail route (`modules/pulls/routes.ts`, the ~170-210 block) is NOT a pure DB read: when a GitHub token is configured it re-fetches the PR from GitHub and DELETE+re-INSERTs the `pr_files` rows on every request. So reusing "the pull's files" by calling that route/service would silently trigger a network round-trip (and DB writes) — invisibly breaking a "no new model call / no network / free" acceptance criterion. `getPrFiles` is a plain `select ... where prId` (see `repository/pull.repo.ts`), and `reviewRepo` also exposes `getPull` (workspace-scoped 404 guard) + `reviewsForPull`. The new `modules/smart-diff/service.ts` composes entirely from those three — zero `container.llm()`, zero GitHub — which is the whole point of Smart Diff (the expensive LLM call already happened in the reviewer; this only regroups). Note smart-diff intentionally takes the SINGLE newest review (`reviewsForPull(prId)[0]`) for its `finding_lines`, which can differ from the PR-list's "current findings PER AGENT" semantics (see the `currentReviewIdsByPr` entry below) — a PR reviewed by multiple agents will badge only the newest run's findings.

- **`ReviewRepository` (repository.ts) wraps `run.repo.ts`** — both files define `completeAgentRun`. When adding a new field to the values type, update BOTH files: `repository/run.repo.ts` (the implementation) and `repository.ts` (the wrapper used by `run-executor.ts`).

- **`GET /repos/:id/pulls` returns `Promise<PrMeta[]>` with NO response Zod schema** (only `params: IdParams`). Adding a field to `PrMeta` is therefore a pure type change — the object is serialized as-is, nothing strips unknown keys. ### 2026-07-08 — Intent Layer convergence: path-traversal guard + references.ts split
- **`container.git.readFile` (`adapters/git/simple-git.ts:129-130`) has NO path confinement of its own** — it's a bare `readFile(join(clonePathFor(repo), path), 'utf8')`. The old `resolvePlanRefs` (formerly in `signals.ts`) extracted repo file paths straight out of the attacker-controlled PR body via `PLAN_PATH_RE` (whose char class allows `.` and `/`) and passed them directly to `readFile` — a PR body containing `docs/plans/../../../../../../etc/passwd` would read arbitrary local files and feed the content to the LLM. Any future caller of `container.git.readFile` with a body-/user-derived path needs its OWN guard before the call — the port itself does not protect you. Fixed by adding `isSafeRepoPath` (`modules/intent/references.ts`) applied to every candidate path before `readFile`: normalize with `path.posix.normalize`, then reject if absolute, equal to `..`, starts with `../`, or any segment (`split('/')`) is `..`. Plain relative paths like `docs/plans/intent-layer.md` pass through unchanged.
- Moved link/reference resolution out of `signals.ts` into a dedicated `modules/intent/references.ts` (`resolveReferences`, renamed from `resolvePlanRefs`) to match the reference layout, and added a third source kind — external (non-GitHub) URLs — routed through the already-existing `container.webFetch.fetch(url)` (SSRF-guarded centrally there; never call global `fetch` from a module). Detection: extract all `https?://` URLs from the body, then exclude any that match `ISSUE_URL_RE` (already handled as GitHub issue/PR links in kind (b)) before capping to 3 and fetching.
- **The `..`-string guard is NOT enough — committed symlinks bypass it; confine at the sink with `realpath`.** An attacker's cloned PR repo can ship a git-tracked symlink `docs/plans/x.md → ../../../../secrets.json`; that path has no `..` so `isSafeRepoPath` passes, and `readFile` follows the link out of the clone root (clone root `~/.devdigest/workspace/<owner>/<name>` → the symlink lands exactly on `~/.devdigest/secrets.json`, the SecretsProvider store, whose content then goes to the LLM). Found by the adversarial security review.
